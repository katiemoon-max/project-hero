# /hero-0-setup — course onboarding (stage 0)

First stage of the Project Hero lifecycle: **setup → research → write → check → publish** (`/hero-0-setup` → `/hero-1-research` → `/hero-2-write` → `/hero-3-check` → `/hero-4-publish`, with `/hero` re-orienting at any point). There is no vault stage: research works straight from the artifacts this stage produces plus the converted corpus, which is why stage 0 is thorough — every evidence layer the waves rely on is either created or kicked off here.

Everything course-specific is captured HERE, in `project.json` — the single source of truth for every later stage. The downstream stage prompts are subject-agnostic and must not need editing per course.

**First acts, before §1:** create the project directory skeleton (`research/`, `knowledge-files/`, `prompts/`, `scripts/`), copy the prompts and scripts in from `templates/` (§5's converter and §6's merge script are run from the project's own `scripts/`, so they must exist before the sections that call them), instantiate `project.json` from `templates/project.json.template`, and **`git init` the project directory and commit the scaffold (F42/F63/F66)**. The pipeline assumes a git baseline exists and nothing previously created one: without it `fixer_diff_sweep.py` cannot run (it now fails loudly rather than printing a false "clean" — on 1PH0 the step-4 gate was decorative for the entire build), a fixer's self-report cannot be checked against `git diff` (F66), and the build has no rollback point. Commit at stage boundaries thereafter — in particular the pre-fixer masters (see `/hero-3-check`). `project.json` is filled **incrementally** — every ruling is recorded the moment it is made, never held in conversation until §8 (rulings held in the head across sections are exactly what gets lost).

## 1. Course facts (ask; verify everything the user asserts)

| Item | How to verify |
|---|---|
| Board, qualification, subject, spec code, course name | user |
| Cobalt course id (`crs_…`) | `getCourseStructure` — confirm the section/topic/subtopic/spec-point tree loads |
| Model policy | default: Sonnet research/fixers/upload · Opus writers · checker = strongest available (never below Opus 5); record any override |
| Skills flag line for this subject (`template.skills_line_label`) | e.g. "Mathematical skills" for sciences/maths, "Source-analysis skills" for history, "Practical skills" for PE — plus the no-skills marker phrase (`template.no_skills_marker`) research packs use internally |
| Paper codes and names; which sections/topics map to which papers; level designations | **the specification itself** (the §4 notebook or the converted spec) — the user *confirms* what the spec states; never accept these from memory (F25). The trap is topic/paper overlap: 1PH0's Topic 1 sits on BOTH papers, a from-memory answer gives the clean split, and every Topic 1 note then carries wrong paper codes into every citation downstream. Record as `course.papers` / `course.levels`; research briefs and writers read them from here |

## 2. Structure snapshot + ratification (HARD GATE is the user's ratification — the tracker cross-check runs where one exists)

The Cobalt structure is the skeleton for everything downstream — every research pack, knowledge file and upload is keyed to a Cobalt spec-point id, so getting this right up front is what kills the content↔CMS mapping problem. But **Cobalt is not ratified blind**: the user always ratifies before anything is written, and the tracker cross-check is the best evidence for that ratification whenever the course has a Master Syllabus.

1. Save the full `getCourseStructure` tree to `cobalt-structure.json` (sections → topics → subtopics → spec points, all ids and names verbatim).

   ⚠️ **Cobalt lookups are keyed on ids, never on names (F21).** Cobalt's own stored spec-point names can carry trailing spaces. `getCourseStructure` trims them on the way out; `searchQuestions`' `spec_point_name` filter matches exactly — so a name read from `cobalt-structure.json` and fed back to a search returns an **empty result set that looks identical to "this spec point genuinely has no questions"** (1PH0: `"Momentum"` → 0 questions, `"Momentum "` → 10). Every sweep in this pipeline keys discovery on `spcpt_`/`sbt_`/`topic_` ids; names are for headings only, and take the trimmed `getCourseStructure` form. If a name-keyed search is ever unavoidable, run the trimmed **and** untrimmed forms and reconcile. Note the artefact lives in Cobalt's own data, not the tracker — the opposite of what a name-mismatch cross-check would lead you to assume.

2. Ask whether the course has a Master Syllabus tab in the subject tracker — and **name the tracker explicitly**: ask the user for the tracker spreadsheet's name/URL rather than assuming they (or a future reader) know which spreadsheet "the subject tracker" is; record it as `paths.syllabus_cross_check`. If it does, get it as a cross-check: **prefer a downloaded CSV** (most token-efficient — ask the user to File > Download > CSV); fall back to the Google Sheet via URL or Drive MCP if a download is awkward. **If the course has no Master Syllabus, do not block**: skip the §2.4 diff and ratify from the Cobalt tree alone — the §2.3 non-content classification and the duplicate-definition check both work from the Cobalt side and still run. Record the absence as a dated ruling in `structure.cross_check_findings` (an explicit decision, never a silent skip).
3. **Filter non-content rows yourself — do not ask the user to ratify them one by one.** Tracker tabs and Cobalt trees both carry rows that are not content to write against — video placeholders above all (names like "Video of …", "Video: …", "… video"). Classify these automatically: `no_content: true` on the Cobalt side, excluded from the cross-check counts on the tracker side. Present them as a single FYI list inside the ratification summary — "N video rows auto-marked no-content; tell me if any of these is wrong" — so the user confirms them in one glance. The per-item ratification ask is reserved for genuine discrepancies. Expect the tracker's own header count to exclude these rows (1PH0: the tab's row 1 says 303 against 306 data rows — it counts content rows only); a count mismatch of exactly the excluded rows is confirmation the filter worked, not a defect.
4. **(Tracker courses) Diff the two on the normalised spec-point DESCRIPTION, not the name, and present the discrepancy report to the user.** Names are neither unique nor a reliable proxy for content (F15, 1PH0: three names each appear in two sections — a name-keyed diff pairs those rows arbitrarily — and `Mechanical Loss`/`Wasted Energy` duplicate content verbatim under *different* names, invisible to a name check). Descriptions come from `findRevisionNote` (returns each spec point's name + definition); `getCourseStructure` returns names only. Compare on a normalised definition string (whitespace/case/punctuation-folded), **not the whole body**. Flag, at minimum:
   - Spec points in Cobalt but not the tracker (after the §2.3 filter) — CMS entries with nothing to write against; needs a user ruling
   - Spec points in the tracker but not Cobalt — content the CMS may be missing; needs a user ruling, not a silent skip
   - Name mismatches (fold curly apostrophes and case before flagging; Cobalt names are authoritative for headings — record genuine differences as aliases)
   - Per-subtopic SP counts on both sides, and subtopic names containing colons (YAML double-quoting rule downstream; also note macOS Finder renders a colon in a filename as a slash, so a file that looks like a nested path is a single file — common on Core Practical / "Topic: subtitle" names)
   - **Duplicate spec points** — same normalised definition appearing under two or more Cobalt ids. This check is Cobalt-side only, so run it even on a no-tracker course. This is *intended teaching design* on two-year courses (the later instance re-teaches the same content with extra context layered on), not a CMS defect: **classify each group as ONE spec point** (definition-match, not full-body-match — the longer body is enrichment, not a separate SP), don't flag it as a discrepancy
5. **The user ratifies the proposed structure before anything is written.** Surface detected duplicate groups as a single FYI list inside the ratification summary — the same one-glance pattern as the §2.3 video rows ("N duplicate-definition groups classed as one SP each; tell me if any is wrong"), never per-item ratification. On a no-tracker course the summary presents the Cobalt tree's shape (section/topic/subtopic/SP counts), the auto-classified no-content list and any duplicate groups — the ratification step itself never disappears. Record the ratification date, the discrepancy list (or the no-tracker ruling), the duplicate groups and the rulings in `project.json` → `structure`. A discrepancy resolved here costs one question; discovered in a wave it costs a rewrite.
6. Generate `sp-mapping.json` mechanically from the ratified tree — subtopics keyed by Cobalt id (name, section, topic, sp_ids) and the mapping array carrying each SP's verbatim name and spec text. Include the SP numbering (`[S.T.Sub.SP]`, 4-level decimal) and the derived legacy filename field — unused on fresh builds, but it is what `/hero-1-research`'s adopt-a-legacy-vault path reconciles against. Carry the `no_content` flags into the mapping so writers and checkers treat those SPs as correctly empty. **Where the course has tiers/levels that apply per spec point** (e.g. Edexcel GCSE higher-tier-only material, marked in bold in the printed spec), carry a per-SP tier/level flag into the mapping too, sourced from the tracker's machine-readable column — bold markings do not survive text extraction (NotebookLM's `source_get_content` strips formatting), so the notebook cannot supply them, and without the flag every note is written tier-blind (F25: 49 of 306 1PH0 SPs are higher-tier only, 94 physics-only). **The flag's shape is `true | false | "partial"` with a `tier_note` carrying the boundary in words wherever it is `"partial"` (F50)** — boards bold at *sub-statement* granularity, so a bare boolean cannot represent "the collision half of this statement is Higher, the equilibrium half is not" (1PH0's 2.23), and no boolean value is correct for such a statement. **Detect the partials mechanically (F44):** any statement whose Cobalt spec points disagree on the tier flag while sharing one spec text is a split statement — on 1PH0 that query returns 2.23 and nothing else. Adjudicate each at the spec PDF's font spans, and **record the tier source explicitly in `project.json` → `course.tier_source` (F59)** — the converted spec can never supply tier (bold does not survive docling), so name the source no writer should have to rediscover. **Duplicate groups get a `primary_id` + `alias_ids` shape**: one knowledge file and one write per group, but every Cobalt entry still exists and still needs publishing — the mapping must carry *every* id the single file satisfies, so checkers don't report an alias id as unwritten and `/hero-4-publish` writes to all of them.

   ⚠️ **Structure comes from the ratified `getCourseStructure` tree ONLY — never from `findRevisionNote`.** `findRevisionNote` returns `subtopic_ids` as an array, and revision notes are shared across courses (e.g. 1PH0 ↔ 1SC0 Combined Science), so those arrays can carry subtopic ids that do **not** belong to this course. Use `findRevisionNote` for definitions (§2.4) only; anything that builds structure from it will silently import foreign subtopics.

## 3. Source PDFs on disk (HARD REQUIREMENT — a NotebookLM notebook alone is not a corpus)

Every research stage greps and quotes **locally converted markdown**: R2 reads the local QP/MS corpus unconditionally in every research mode, and `research_mode: nlm` covers a missing **ER** corpus only. A course whose papers exist only inside a NotebookLM notebook cannot start a single wave — this blocked a real onboarding once, so verify it now, not at `/hero-1-research`.

1. **Inventory what is on disk**: every sitting's question paper and mark scheme as PDFs (or already-converted `.md`), plus examiner reports where the board publishes them, **plus the specification PDF itself** — §7 reads the spec's skills table directly and F27's failure modes make the notebook unusable for that read, so the spec belongs in the disk corpus, not just the notebook. Record the corpus location as `paths.corpus_root` **and the specification PDF's own path as `paths.specification_pdf` (F60)** — tier font-span checks and the coverage gate must open it, and a gate should never have to glob for its input.
2. **If PDFs are missing, walk the user through acquisition before anything else proceeds:**
   - Bulk-download from the exam board's past-paper pages with a Chrome bulk-PDF-extractor extension (works well for Edexcel courses)
   - Where papers are login-gated on the board site (common for recent sittings), the user's teacher-portal login or the SME internal paper store are the fallbacks
   - Pulling text back out of NotebookLM via `source_get_content` is a LAST resort — you get NLM's extraction instead of a controlled conversion, and it needs the user's explicit go-ahead
3. Move on only when the QP/MS inventory is complete for every sitting. Missing ERs are fine (they set the research mode at §5); missing QPs or MSs are not.

## 4. NotebookLM notebook

1. Ask whether a notebook exists for this course; if not, walk the user through creating one in the NLM web UI and uploading sources: all past papers, mark schemes and examiner reports (the PDFs from §3), the specification PDF and the extracted Cobalt content file (§6 — upload it once the extraction finishes).
2. Sources renamed to clear paper-code names (e.g. `1PH0 Paper 1H – 2024 June – Mark Scheme`) — ambiguous names cause fabricated citations downstream.
3. Verify **directly against the notebook**: `mcp__notebooklm__notebook_get` returns the title and full source list, proving it is populated and reachable. Record `corpus.notebook_id` in `project.json`. Note absent/duplicate/variant sources (e.g. "Revised Mark Scheme" replacing "Mark Scheme") → `corpus.known_casualties` as source titles.
4. **Diff the notebook source list against the §3 disk inventory (F16).** The two inventories drifting apart is the normal case, not the exception — the notebook accretes over time, the disk corpus is built once, and each alone looks complete. List notebook sources with no disk counterpart and disk files with no notebook source; resolve what you can now (acquire missing PDFs per §3, upload missing sources), and record any remaining gap in `project.json` → `corpus.notebook_disk_gap`. This matters because R2 reads **local converted markdown unconditionally** — a notebook-only sitting is invisible to research however complete the notebook looks (1PH0: 24 documents across three sittings were in the notebook and not on disk).

## 5. Corpus conversion — kick off now, gate later

The research stages grep and quote **local converted markdown**, never raw PDFs — converted `.md` (and CSV) cost a fraction of the tokens of any other format and make every quote verifiable by construction.

**Mark schemes are tables, and the conversion is the only thing R2 ever sees.** A flat text-layer extractor destroys them silently — see the table-integrity gate at step 2, which is not optional.

1. **Convert the §3 PDFs with `scripts/convert_pdfs.py`** (table-structure recognition on, OCR off — resumable via a first-line marker, writes `<name>.md` next to each `<name>.pdf` with one `## Page N` section per page, flags scan-only docs that need OCR or a PDF-direct fallback). **Engine choice is per DOCUMENT TYPE, never per corpus (F64):** the script uses docling for QP/MS/ER and **pymupdf4llm for files matching `--spec-pattern`** — docling drops bold, and boards use bold semantically in specifications (F44), and it also silently lost spec statement content in production (F58: `g energy` vanished from 2.4; three whole sub-items across one spec). The docling-vs-pymupdf4llm result **inverts** between mark schemes and question papers (docling loses QP figure-internal text — 3,255 content tokens across 21 papers on 1PH0; pymupdf4llm loses MS guidance words), so never swap wholesale in either direction, and **any engine deviation must record what its benchmark actually tested** — the 1PH0 deviation benchmarked mark schemes and generalised to all three types. If a benchmark on this board shows neither engine dominates a type, run both: the second extraction goes in a **parallel tree** (e.g. `research/corpus/pdf-second-engine/`, so nothing globbing `*.md` sees two files per paper), recorded in `corpus.second_engine_pass` as *evidence for absence-claims, never the citable corpus*. Usage: `python convert_pdfs.py <corpus_root>`; add `--subdir "Unit 1"` to shard, `--limit 3` to smoke-test first. It **overwrites `.md` left by any other converter**, so a corpus carrying an older text-layer conversion upgrades in place on re-run. Budget **~2–3 s per page on CPU** and a one-off ~500 MB model download — start it now, as background agents, so it runs while the rest of setup completes. Convert ERs too where they exist; if the ER corpus is missing or unconverted, set `research_mode: nlm` (that is the only thing `nlm` covers).
2. **Conversion gates (HARD — the converter enforces all three, do not talk past a failure).** The run exits non-zero and prints the failing gate:
   - **Table integrity (F17):** any mark scheme converted to **zero pipe characters** fails — a mark scheme with no pipes has no table left, whatever its character count says. Also fails if *no* file matched the mark-scheme name pattern, because a gate that checks zero files passes vacuously; pass `--ms-pattern` when a board names its schemes unusually, and check the count it reports is the count you expect.
   - **Legibility (F32):** any file that is mostly glyph-index lines (`## /0 /1 /2 …` — a non-standard font encoding the engine could not decode) or contains zero lines of corpus vocabulary fails. This class **passes the table gate and looks complete** — two 1PH0 examiner reports were 80% and 76% glyph-index lines and every downstream brief counted them as usable, because a silently unusable file produces *thin results that look like genuine thinness*. **Record every legibility failure in `corpus.known_casualties` with the reason, from the report's `legibility_failures` list** — that list is what every later brief is built from; it must be generated, not remembered.
   - **Spec bold (F44):** a specification whose source PDF carries bold spans while the converted markdown carries no `**` fails — the tier marking did not survive, and a spec with no bold looks exactly like a spec with no Higher-tier content.
   Re-audit an already-converted corpus with `python convert_pdfs.py <corpus_root> --verify` (reads `.md` only, converts nothing). The report also carries a **report-only orphan-part check (F62)**: non-sequential part labels in a question paper (a `(ii)` with no `(i)`) mean the conversion dropped a stem, figure or part — read each flagged file against its PDF before any stage asserts an absence from it. Per-file evidence lands in `conversion-report.json` at the corpus root — cite it when you set the status at step 5.
   ⚠️ **Why this is a gate and not a spot-check (F17, 1PH0):** the text-layer converter this replaced reported success on every file, produced non-empty plausible-looking markdown, and had destroyed every mark-scheme table in the corpus. Question order scrambled ("Total for Question 1 = 6 marks" printed *before* "1 (a)"), "Additional guidance" detached from its marking point, mark allocations floated unanchored to any row, and `a = (v−u)/t` flattened to four bare lines with **the minus sign silently dropped** — wrong physics, not lost formatting. Nothing downstream checks table integrity, so a course can run all the way to publish on a corpus where every mark-scheme quote is unreliable. Benchmarked on one 30-page mark scheme: text-layer 28,100 chars / **0 pipes**, docling 69,682 chars / **829 pipes**.
3. **Read the report's Unicode audit, then spot-check what it points at (F20).** The conversion report counts, per file, the artifact classes that survive a passing table gate: mojibake/replacement chars, ligature glyphs (ﬁ/ﬃ), Private-Use-Area symbol-font characters (U+E000–F8FF) and math-alphanumeric glyphs (U+1D400–1D7FF). A mechanical count over the whole corpus beats an eyeball pass of 2–3 files — the 1PH0 corpus carried **910 dropped symbol-font characters**, including a Symbol-font tick marking the correct MCQ option; had that tick been the only record of the answer, R2 would have extracted MCQ schemes with no answers and nothing downstream would have caught it. So: open the files with the highest PUA counts and check whether any glyph is the *sole carrier of meaning* (recover those from the PDF and record them in `corpus.known_casualties`); redundant glyphs (tick beside an answer letter) are benign. ⚠️ PUA characters return **zero to a plain grep** — a clean grep near one is a false all-clear; trust the report's counts (or Python), never a grep. Also read one mark scheme's marking-point table: question ref, marking points and tariff should sit in **one row**. The research prompts carry the in-flight countermeasures (mojibake recovery in R2, ligature/PUA rules in R2, the symbol sweep in CHECKER) — but the audit here is the primary sweep, not the prompts.
4. Record in `project.json`: `corpus.kind`, the unit/file naming conventions, sitting variants (e.g. "(A)" resits are separate sittings), and casualties as they surface (file paths for local files, source titles for notebook sources — never cite either kind).
5. Track `corpus.conversion.status` (`pending → running → complete`). **`complete` requires all three conversion gates passing**, not just a finished run — record the gate verdict alongside the status. **`/hero-1-research` gates on `complete`** — waves must never start against a partial or table-less corpus.
6. **Spec-completeness gate (F58/F59 — HARD wherever the course has a tracker).** Diff the converted specification against the tracker's authoritative definition column, statement by statement: every tracker statement ID must resolve in the conversion, and every content word of the tracker's statement text must appear in the conversion's statement body (the tracker is abridged, so the reverse direction is noise — **tracker = completeness authority, spec PDF = wording and tier authority, PDF adjudicates disagreements**). This is one text comparison with no PDF engine, and on 1PH0 it would have caught every loss the five-stage pipeline missed: dropped sub-items (`g energy`), truncated equations, and 16 Physics-only statements whose table rows no ID-keyed lookup could parse. Three rules that came out of building it:
   - **Assert the denominator (F59):** any ID-keyed sweep must match the board's full ID grammar (`\d+\.\d+[PH]?` — suffixed Physics-only/Higher statements silently fell outside a bare `\d+\.\d+` sweep, which then reported a clean pass over a third of the specification), and must check its statement count against the tracker's total. A check that cannot state its denominator passes over content it never read.
   - **Validate table SHAPE, not just cell contents:** rows with an empty ID cell, or ID and statement fused into one cell, are mechanically detectable and were 16 of the 22 defects found on 1PH0 — *present but unreachable* text, invisible to every ID-keyed process.
   - **Fix losses at source** in the converted spec with dated ruling notes, then re-run to zero — never patch downstream artifacts.
   Also run the two setup-time coverage checks (F60): **(A) allocation** — every spec statement has a subtopic home in the tracker AND exists in the conversion (1PH0: Core Practical 5.9 was absent from the tracker entirely — nothing on site owns it, so no writer would ever have been launched for it; and 6.19 was reachable only as the typo `6.169`); **(B) split statements** — a statement partially bold in the PDF must have two tracker homes, one tiered and one not; where PDF bold extent and the tracker's split disagree, one source is wrong — adjudicate now. A tested implementation of A/B (plus the per-wave checks C/D — see `/hero-4-publish`) exists as `scripts/spec_coverage_gate.py` from the 1PH0 build; run it where present, run the checks by hand where not — **the gate must run either way, and a check that cannot run fails the stage rather than skipping**.

## 6. Cobalt commentary extraction — kick off now (never defer silently)

Research packs carry the CMS's existing per-question commentary — `$c{…}` blue-text Commentary and Examiner Tips & Tricks — extracted into one file grouped by spec point. `/hero-1-research`'s R1 evidence assembly slices that file per spec point; a null path with no ruling silently costs every research pack that layer, which surprises everyone downstream. So the extraction is a setup-stage job:

**The output schema below is verbatim and mandatory (F22).** The extraction runs as parallel agents by design, and a loose prompt does not mechanically merge: in production, thirteen agents given the same schema-free prompt produced two spec-point heading formats and three part-attribution formats. Both failure modes were silent — a merge keyed on `qstnprt_` lost every shard that omitted the ids, and a heading regex without optional backticks dropped two whole sections (162 of 659 entries) while the merged file still looked completely well-formed. The loss was caught only by reconciling input header counts against output header counts.

1. Kick it off now — parallel background agents (one per section is the proven shape), or its own session if this one is heavily loaded (it is a big MCP crawl over every published question in the course). Prompt per agent:

```
Extract all commentary and Examiner Tips & Tricks from section [SECTION] of
[COURSE] in Cobalt, using the sme-content MCP.

Discovery is keyed on IDS, never names: walk the section's subtopic/topic ids
from cobalt-structure.json and pull each subtopic's questions. Never key a
search on spec_point_name (F21: stored names can carry trailing spaces that
searchQuestions matches exactly — a name-keyed sweep returns an empty result
set that reads as clean coverage).

For every published question and question part, extract:
- Commentary — text wrapped in $c{...} sequences (blue text in the Cobalt UI)
- Examiner Tips & Tricks — text between **Examiner Tips and Tricks** and
  **End of Examiner Tips and Tricks**
- Unwrapped solution commentary — teaching prose in the solution field that
  sits OUTSIDE both $c{} wrapping and the Mark Scheme and Guidance block
  (e.g. a trailing misconception paragraph). This class is real content the
  wrapped-only definition silently dropped (F19); label it distinctly so
  downstream consumers can weight it differently.
If you see candidate content fitting none of the three classes, record it in
an end-of-file note rather than dropping it silently.

Output file: [SPEC-CODE]-Cobalt-Content-S[NN].md, EXACTLY this schema:
- One heading per spec point: `#### <Spec point name> (spcpt_xxxxx)` — name
  and id verbatim from cobalt-structure.json, plain parentheses, NO backticks
- Under it, one entry header per extract:
  `**<Commentary | Examiner Tips and Tricks | Unwrapped solution commentary>**
  — qstn_xxxxx part (b) — qstnprt_xxxxx`
  then the verbatim text. The qstnprt_ id is MANDATORY wherever the part has
  one; a part with genuinely no id is marked `no-part-id`
- A part tagged to two spec points appears under BOTH headings — that is
  correct content, not duplication
- Do NOT emit subtopic headings, and NEVER write method/cross-check notes at
  heading level — the merge script rebuilds the subtopic layer (F28)
```

2. **Merge with `scripts/merge_cobalt_shards.py` — never by hand, never ad hoc.** The script rebuilds the `### <Subtopic> (sbt_…)` layer from `sp-mapping.json`, so every spec-point block sits under its own subtopic by construction — F28: a crawl-order merge bled 63 subtopics' blocks under neighbouring headings (or under an agent's own "Method and cross-checks" note), which fabricated sibling-boundary disputes downstream that two agents then spent sweep effort resolving. It dedups on `(spec_point_id, kind, part_key)` — never on part alone, since a cross-tagged part legitimately appears under both spec points — and **fails unless `input entries − duplicates == output entries`** and every shard `spcpt_` id exists in the ratified mapping.
3. **The merge is re-runnable, and a stale merge is the trap (F23).** A shard corrected *after* the merge silently never reaches the merged file — and every count-reconciliation still passes on the stale output (proven in production: a re-merge changed 370 lines while entry totals were identical either way). Re-run the merge whenever a shard changes, and tick this stage **against the merge, not the extraction**. `/hero-1-research` runs `merge_cobalt_shards.py --check` at its entry gate (non-zero exit when any shard is newer than the merged file) and re-merges before anything reads `paths.cobalt_content`. If a stale merge already reached the notebook, replace the source; if deleting the old source needs a ruling (`source_delete` is irreversible), rename it `SUPERSEDED — DO NOT CITE` instead.
4. Record the merged path as `paths.cobalt_content`, and upload the merged file to the notebook as a source (§4).
5. If there is genuinely nothing to extract (e.g. the course has no published questions yet) or the user explicitly rules it out, record `paths.cobalt_content: null` **with a dated ruling** in `structure.cross_check_findings` — an explicit decision, never a silent deferral.

## 7. Per-SP skills map (direct spec read — never NotebookLM)

The knowledge files carry a per-spec-point skills line (`template.skills_line_label`), and the mapping of skills to spec points comes straight out of the specification document — most boards print it per spec point (a maths-skills column, appendix references, or an integrated-skills grid).

1. Read the mapping directly from the converted specification (or the spec PDF) and write `skills-map.json`: every ratified Cobalt SP id → the verbatim skill codes/wording, or an explicit no-skills entry — a blank cell in the spec's table is meaningful data, not missing data. Record the path as `paths.skills_map`.
2. ⚠️ **Never derive this mapping via NotebookLM — it fails in two independent ways (F27).** NLM has shifted a spec table's skills column by one row in production (1PH0, 2026-08-05) — every SP inherits its neighbour's skills and the error propagates silently into every knowledge file. It has also **truncated** a cell with no warning (statement 2.11: 10 of 12 codes returned, `4a, 4c` silently dropped) — and truncation is *harder to catch than the shift*: a shifted column is detectable by eye once you know to look, while a truncated cell is a correct-looking, internally consistent answer that survives spot-checking unless you compare against the printed row. Direct read of the printed table only.
3. **Join Cobalt SPs to spec statements on statement number with a wording fallback (F26).** Cobalt `spec_text` statement numbers can be malformed in Cobalt's own data (1PH0: SP 6.2.5.2 opens `6.169` for the spec's `6.19` — wording matches verbatim, the number has a stray digit, and it is close enough to a real number to look plausible in review). A number-keyed join silently drops such SPs — the 1PH0 skills map would have shipped one SP with no skills at all. Fall back to a wording match, and report every SP whose number failed the join as a **Cobalt data correction for the user** — the pipeline never patches CMS data itself.
4. Cross-check the count: SPs with skills entries plus SPs with explicit no-skills entries must equal the ratified SP count. An SP absent from the map is a gap to fix now, not downstream.
5. If the subject genuinely has no per-SP skills mapping in its specification, record `paths.skills_map: null` **with a dated ruling** (same pattern as `paths.cobalt_content`) — R1 then omits the skills layer by explicit decision, never by silent absence.
