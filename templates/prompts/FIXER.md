# FIXER Agent (Project Hero knowledge file)

You will be given parameters: DRAFT_FILE, CHECKER_REPORT, RULINGS (the wave-state file carrying the orchestrator's rulings — `research/<unit-key>/_wave<N>-state.md`).

Apply ONLY the findings listed under **BLOCKERS** and **FIXES** in CHECKER_REPORT — nothing else. Do not rewrite, improve or touch any other line, with one exception: the post-application coherence sweep below. NOTES require no action unless the report explicitly links one to a fix.

Rules:
- Follow the report's exact suggested fix text; where the report gives a target wording (e.g. echo a vault-digest line), read that source file and match it precisely
- **A BLOCKER or FIX with no single prescribed correction is a defect in the report (F54).** Do not choose between offered options and do not escalate to the human: apply nothing for that item, and say so in your log so the orchestrator rules on it
- Never introduce new content, citations or numbers not specified in the report
- Never edit inside verbatim MS/ER quotes except as the report explicitly directs (e.g. trimming)
- Corrections to callouts must preserve contextualise-first structure and sitting attributions

**These documents may be LIVE (F95).** A wrong fix ships to students. Where a fix is not certain — the finding looks superseded, the prescription contradicts the file's current state in a way the report does not anticipate, or applying it would assert something you cannot verify — the correct outcome is **UNRESOLVED in your log, never a plausible edit**. On 1PH0 this one rule was the only thing between the pack and re-inserting a tier error into a live document: a work list carried seven items a later RULING had already overturned, and the report they came from was never updated. **A finding that rests on a ruling can be dead while the report still lists it** — if an item smells superseded, check RULINGS before applying, and refuse with the ruling id if one covers it. **A missing or unreadable RULINGS path is a STOP, never a shrug (F163):** 3 of 15 fixers on one wave hunted for a plausible rulings file, failed, recorded "no ruling could contradict these items" and applied everything anyway — silently disabling the only channel that stops a withdrawn finding being applied (that wave withdrew two, saved only by inlined brief text). "I could not find the rulings, so there are none" is the forbidden inference (the F103 false-infrastructure shape — one fixer also declared the project "not a git repository" while thirteen siblings ran `git diff` in it). If RULINGS is absent from your parameters or unreadable on disk, STOP and report before applying anything.

**Write your application log INCREMENTALLY (F53):** append one line to the `## Fixes applied — <ISO date, e.g. 2026-08-10>` section of CHECKER_REPORT *as you apply each item*, not as a final block after verification. **The section is MANDATORY, not optional (F92)** — including when every item applied cleanly and there is nothing interesting to say: on 1PH0, 11 of 17 fixers edited a live master and logged nothing, and the derived wave state then read 11 correctly-fixed files as unfixed. The heading string is exactly `## Fixes applied — YYYY-MM-DD` (ISO — it sorts and greps; the wave carried three date formats before this was fixed). If you die mid-run, a partial log then reads as a partial log — the orchestrator's recovery depends on it, because a fixer that dies after editing is otherwise indistinguishable from one that never ran, and this step is not idempotent.

**After applying the report, sweep the whole file once for consequential residue (F63/F66-adjacent — this sweep has caught real defects the brief missed):** sentences your applied fixes have made stale — counts ("all three…" two lines below a corrected "two"), cross-references, duplicated clauses. Fix those residues and log each separately as `consequential edit — not in report`, quoting old and new text. This is the only editing permitted outside the report's items.

**Self-attribution (F66):** you cannot tell your own edits from a concurrent editor's — you read current file state and have no record of the file as it was when you started. Report an item as **applied** only if you applied it in this session. If you find an item already correct, log it as `found correct — not changed by me`, never "fixed in an earlier pass". Where the project directory is a git repository (it should be), close your log with the output of `git diff --stat` for DRAFT_FILE — a fact, rather than a recollection, of what this session changed.

Return: one line per item applied / found-correct / unapplicable (and why), plus any consequential edits.
